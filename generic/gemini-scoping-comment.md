Before making any code changes, run a Gemini scoping pass using the full
repository root as context, then post the result as a comment on the active
issue or PR.

Inputs
- Task: `<TASK>`
- Repository root: `<REPO_ROOT>`
- Active target: `<ISSUE_OR_PR_URL_OR_NUMBER>`

Required worker model
- Keep the current shell as coordinator.
- Start a tmux worker to coordinate the scoping handoff and comment posting:
  - `tmux new-session -d -s gemini_scope_codex "cd <REPO_ROOT> && codex --yolo"`
- If needed, start a separate comment-posting worker:
  - `tmux new-session -d -s gemini_scope_comment_codex "cd <REPO_ROOT> && codex --yolo"`
- Do not start implementation workers until the Gemini scoping comment has been
  posted.

Instructions for Gemini
- Analyze the full repository root, not just a few guessed files.
- Use the repo structure, README files, AGENTS instructions, docs, configs,
  scripts, tests, and relevant source files to build context.
- Prefer repo-root-relative file references in all findings.
- Do not implement anything yet. This is a scoping-only step.

Required output
Produce a markdown scoping report with exactly these sections:

1. Task Restatement
- Restate the task in repository-specific terms.

2. Relevant Areas
- Identify the most relevant directories, modules, services, docs, scripts, and
  tests.
- Include repo-root-relative file references for each item.

3. Likely Touch Points
- List the files most likely to need changes.
- For each file, explain why it is likely in scope.

4. Dependencies and Impact
- Identify upstream and downstream dependencies, integration points, shared
  abstractions, configs, migrations, background jobs, frontend and backend
  coupling, tests, and operational concerns that may be affected.

5. Risks and Unknowns
- Call out ambiguity, missing context, risky assumptions, unclear ownership,
  and areas where the codebase may have hidden coupling.

6. Suggested Execution Plan
- Provide a minimal step-by-step plan for implementation.
- Include recommended validation steps and the smallest relevant test scope.

7. Open Questions
- List only questions that materially affect implementation.

Comment requirements
- Post the full scoping report as a comment on the active issue or PR before
  implementation starts.
- Put this disclaimer at the top of the comment:

  `Disclaimer: This scoping report was generated by Gemini using a large repository context window. It may be useful for orientation, but it must be verified against the codebase and should not be followed blindly.`

- Use repo-root-relative file references in the comment body.
- If the active target is an issue, post to the issue.
- If the active target is a PR, post to the PR.

Suggested GitHub commands
```bash
gh issue comment <number> --body-file <comment_file>
gh pr comment <number> --body-file <comment_file>
```

Rules
- Be concrete, not generic.
- Reference files explicitly.
- Prefer breadth-first scoping before narrowing down.
- If multiple implementations are plausible, name the options and say which one
  seems most consistent with the repository.
- If the repository contains prior related work, call it out with file
  references.
- If some areas were not inspected despite the large context window, say so
  explicitly.

Stopping condition
- Do not begin implementation until the Gemini scoping report has been posted.
